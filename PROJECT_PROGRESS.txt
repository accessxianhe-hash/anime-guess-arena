用途
- 这个文件用于给后续新对话快速同步项目现状。
- 新进度应建立在旧进度基础上更新；允许把已经过时的旧进度替换为当前事实。
- 修改范围应尽量写清楚：本地文件、服务器路径、是否已部署、是否需要用户手动操作。

半自动更新规则
- 以后默认按半自动方式维护本文件。
- 需要自动更新的情况：
  1. 修改了代码、脚本、配置或文档，并且这些改动会影响后续接手。
  2. 完成了正式服务器部署、同步文件、重建容器、健康检查或服务器清理。
  3. 确认了域名、DNS、服务器路径、部署方式、脚本版本、外部服务状态等关键事实。
  4. 用户明确要求记录某个决策、结论或排查结果。
- 不自动写入的情况：
  1. 临时排查过程、未验证猜测、一次性命令输出。
  2. 很小且不会影响后续接手的聊天结论。
  3. 已经被后续结论覆盖的中间状态。
- 更新方式：
  1. 优先替换过时内容，不无限追加流水账。
  2. 新增内容要写清楚“本地是否已改”“服务器是否已同步”“是否需要用户手动操作”。
  3. 每次更新后把“更新时间”改成当前日期。
- 安全规则：
  1. 不记录密码、Token、Cookie、完整数据库连接串、私钥内容。
  2. SSH 命令可以记录到 key 文件路径级别，但不记录私钥内容。
  3. 如果必须描述敏感配置，只写用途和位置，不写具体密钥值。

代码改动提交说明规则
- 以后每次有代码、脚本、配置或重要文档改动时，默认给用户提供中文提交说明。
- 提交说明至少包含：
  1. Summary：一句话标题，适合填 GitHub Desktop 的 Summary 输入框。
  2. Description：分点说明主要改动、部署/验证状态、需要用户手动操作的事项。
- Summary 应简短具体，优先描述用户可感知结果，不写空泛词。
- Description 不写无关排查细节，不写敏感信息。
- 如果一批改动包含多个功能，应合并成一个清晰主题；必要时建议用户分多次提交。
